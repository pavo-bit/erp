## 1. Traceability Framework & Classification Standards

Every documented, claimed, and implemented requirement across the 25 functional domains of the Multi-School SaaS ERP is mapped below. In strict adherence to integrity guidelines, each requirement is classified into exactly one status:

- **`IMPLEMENTED_AND_VERIFIED`**: Full source code implementation exists, APIs are wired, authorization/RLS is enforced, relevant portal UI is bound, and automated tests pass.
- **`IMPLEMENTED_BUT_NOT_FULLY_VERIFIED`**: Backend and frontend code exists but requires physical multi-user load or specialized live hardware to exhaustively prove.
- **`PARTIALLY_IMPLEMENTED`**: Core workflows exist, but edge-case handlers, sub-workflows, or secondary views remain incomplete.
- **`NOT_IMPLEMENTED`**: Feature is specified in theoretical documents but lacks concrete backend routes, database schema, or UI pages.
- **`BLOCKED_EXTERNAL`**: Feature depends strictly on external physical hardware (e.g. physical biometric terminals, physical GPS trackers) or paid third-party cloud accounts (Twilio, Razorpay Live, S3).
- **`DEFERRED_BY_OWNER`**: Requirement was explicitly deferred by the project owner (e.g. Parent native Android mobile app).
- **`NOT_APPLICABLE_WITH_JUSTIFICATION`**: Requirement was superseded or deemed redundant by an architectural decision.
